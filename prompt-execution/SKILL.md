# Prompt Execution

将一份剧本稳定地跑成整组镜头视频的生产调度层。`prompts_structure` 负责“怎么写提示词”，本 skill 负责“先做什么、谁确认、失败了怎么办、经验记到哪里”。

当一场戏已有生成镜头或初剪，需要整体检查叙事、连续性和剪辑节奏时，按 [editing-review/SKILL.md](../editing-review/SKILL.md) 复盘实际片段并确定修改清单；新增或重做镜头再回到本 skill 的逐镜流程执行。

当用户明确在 `ai_image_video_generator` 中使用 **Flux.2 Klein 或由 Codex 直接调用的 GPT 图像模型生图 + MiniMax H3 视频**时，先读 [references/ai-image-video-generator.md](references/ai-image-video-generator.md)。它是该应用的集成档案：说明已实现的接口、资产回填格式和当前仍需人工执行的步骤。它不替代本 skill 的确认门，也不改变其他渲染器的通用流程。

本项目使用 MiniMax H3 时默认选择 **完整 int8 工作流**，提交请求时显式传 `workflow_type: "int8"`。不得因耗时或资源压力而静默切换为 pruned；若 int8 无法运行，说明原因并先与用户确认替代方案。

## 总流程

严格按阶段推进，每个阶段完成并记录后才能进入下一阶段：

0. **风格定义**：选定图像模型（Flux / Z-Image / GPT 等）后，用 2-3 张代表性场景试生成（如一张场景建立镜头、一张人物镜头、一张复杂构图），附上候选风格后缀。用户确认风格前不生成任何概念图或分镜。风格一经确认，全项目沿用同一风格后缀，不中途更换。
1. **概念资产**：基于确认的风格和渲染器生成概念资产。**Flux 和 GPT 的流程不同**（详见 [references/pipeline.md](references/pipeline.md) 阶段 1-2）：
   - **Flux**：每个角色生成两类资产——身份锚图（单人正面照，flux t2i，用于 Flux i2i 关键帧参考）+ 角色概念图（front/back 双栏，用于 MiniMax 视频参考）。场景生成场景锚图（flux t2i，无人）。
   - **GPT**：每个角色直接生成角色概念图（可含多视图，同时用于关键帧生成和 MiniMax 视频）。场景生成场景概念图。不需要额外身份锚图。
   - 用户指定使用 `ai_image_video_generator` 的 Flux 角色概念图功能时，直接在 Free Canvas 的 **Image-to-Image → Skill → Concept Image** 页签中选中该角色唯一的源图，补充必要的角色约束后点击"生成角色概念图"，完整使用应用内置流程。不要把该流程拆成多次手工 Flux API 调用、手工做人脸裁切/放大/拼版；详细行为见 [references/ai-image-video-generator.md](references/ai-image-video-generator.md)。生成后将最终概念图及身份锚图路径回填 concepts JSON 的 `reference_images`。
2. **资产确认门**（可选但推荐）：让用户快速过目角色与场景锚图，气质不对在这里改最便宜。
3. **分镜拆解**：用 [shot-planning/SKILL.md](../shot-planning/SKILL.md) 把剧本大纲或场次拆成 `concepts + shot_breakdown` 两个 JSON。已有概念图时，分镜可参照角色外观和场景空间精确编写 camera/framing/action；概念图尚未完成时先规划可确认的叙事与调度，后续补齐视觉锚点。
4. **分镜确认门**：先把完整镜头表交给用户过目。用户确认前不生成任何关键帧。确认后记录确认结论，后续改动走增量，不重跑全片。
5. **逐镜关键帧**：按镜头顺序生成关键帧，**Flux 和 GPT 的生成路径不同**（详见 [references/pipeline.md](references/pipeline.md) 阶段 5-6）：
    - **生成前必须逐项核对全部相关概念图和镜头连续性**：先查看镜头表及前后相邻镜头的剧本、已确认关键帧/尾帧或分镜；再实际打开本镜涉及的每个角色、entity、道具和场景概念图，不凭记忆或文件名推断设计。明确每个主体的身份、服装/材质、形状细节、空间位置、朝向、视线、动作起点，以及场景摄影机方位和前后镜的动作衔接。若本镜出现已生成概念图的道具，必须实际附上并核对该道具概念图；关键帧中的轮廓、结构、材质、颜色和相对尺寸应遵循概念图，不能只在提示词里提到道具名称后凭空重画。场景概念图是必须核对的空间与固定造型依据，不能只作为可选参考：确认本镜对应的场景视角，逐一锁定雕塑、建筑、池体/水面、入口及其他显著地标的形状、位置和状态；不得在生成时擅自改形或用通用游乐场元素替代。将场景概念图与相邻镜头画面对照，确定两者的视角关系和连续状态；若视图不覆盖本镜机位，结合已确认镜头建立方位，不臆造场景背面。**同时核对环境连续性**：记录相邻镜头已确立的时间（白天/黄昏/夜晚）、天气、天空状态、主光方向与色温、整体曝光/色调，以及地面和环境的干湿、烟尘、水面等状态。剧本未明确写出时间或环境变化时，沿用前镜；只允许剧情要求的局部变化（如能量闪光、爆炸、喷水）覆盖对应区域，不要把整场景改成另一时段、天气或光线。场景概念图确定场景结构和材质，已确认的相邻镜头确定当前连续动作中的环境光照状态。**生成关键帧时还要核对透视和尺度**：逐一比较角色、entity、道具与场景锚点的相对尺寸；有明确设定（如 entity 为人类的约五倍）时按设定呈现，没有明确数值时至少沿用已确认前镜的屏幕比例。考虑近大远小和机位后，仍须确保主体的实际尺度关系清楚，不能让前景人物/水牢因构图占比而看起来比远处的大型 entity 更大。**空间连续性核对对角色、entity 和道具一视同仁：明确主体相对场景锚点的具体位置与接触/遮挡关系（例如池内、池沿、岸上、空中，是否浸入水面，是否落地或悬浮），并沿用前镜已建立的位置；不能只画对主体外观，却把主体放错场景位置。**若不同参考之间有冲突，先判断各自负责的内容：场景概念图负责环境和固定物造型，角色/entity/道具概念图负责主体设计，前后镜关键帧/尾帧负责已建立的镜头空间、环境光照和尺度连续性；在提示词中写明优先关系及必须保留的锚点。只有完成上述核对后才编写关键帧提示词。若当前景别无法清楚呈现关键动作或覆盖范围（如全身护盾），调整构图到能读清动作的范围，并同步镜头表。
    - **确保参考图确实传入生成器**：在提示词里写“参考图1/参考图2”并不等于模型收到了图片。调用图像生成或编辑工具时，必须通过该工具支持的图片输入字段实际附上本地参考文件，并核对输入列表包含本镜指定的前镜画面、场景概念图、角色/entity/道具图；输出后检查设计与构图是否遵循这些图片。未实际附图时，不得把文字中的参考图职责当作已生效。
   - **根据上镜成片逐角色确定本镜关键帧状态**：生成前实际查看上一镜成片的末段/末帧；若本场有多个穿插镜头，还要回看相关动作最初建立的镜头及其末状态。逐一记录本镜出场角色/entity 的画面方位、姿势、移动方向、视线、双手正在做什么、武器/道具持有状态、护盾/伤势状态，以及仍在持续的攻击、受击、聚能或环境运动；区分哪些从上镜延续到本镜首帧、哪些在本镜中改变、哪些已结束。关键帧必须呈现正确的“此刻状态”，不能只画本镜的新动作而丢掉尚未结束的上一动作。例如水柱仍在攻击桃子、她的全身护盾仍承受冲击，而她同时举雷枪反击时，画面要同时交代水柱撞盾、护盾覆盖身体、枪口朝向水精灵及反击动作。按动作所需的可见范围选择景别；近景无法容纳多个必须同时读清的动作时，先调整镜头表和构图再生成。若已生成的前镜与剧本/镜头表中的动作状态冲突，先依据用户已确认的剧情厘清并更新镜头表，再制作关键帧和视频提示词。
   - **Flux**：首选路径——身份锚图 + 场景锚图 → Flux i2i（flux-kontext）。质检不合格时走三段式回退（camera plate + action plate → 合成）。
   - **GPT**：角色概念图 + 场景概念图 → GPT 直接生成关键帧。
   - 遵守 [references/retry-policy.md](references/retry-policy.md)。
 6. **关键帧质检**：逐镜对照已确认的角色、entity、道具和场景概念图，核对身份与造型细节、固定地标几何、摄影机方位、左右站位、空间关系、时间/天气/光线、环境状态、动作起始状态及人物/entity/道具之间的透视和比例；尤其检查概念道具是否被改形、雕塑/建筑/池体等显著固定物是否被改形或替换，并检查本镜整体日夜、天空、主光方向和曝光是否接续前镜（除非剧本明确要求改变）。有明确身高或尺寸设定时按设定核验，否则与已确认前镜对照。任一关键锚点不符就先修提示词重生成，不带废片往下走。
7. **回填镜头表**：关键帧通过质检后，立即把文件路径写入镜头表 JSON 对应镜头的 `reference_images`。概念资产（角色/场景/道具锚图）生成后同样回填 concepts JSON。保持 JSON 与磁盘产物实时一致，前端和后续 agent 读到的永远是最新状态。
8. **逐镜视频**：用合格关键帧 + 角色/场景锚图组装视频提示词并提交，同样遵守重试策略。MiniMax H3 默认使用**纯多参模式**：把关键帧、人物/场景/entity 概念图按约定顺序放入 `reference_images`，并在提示词中逐图说明职责；不要传 `first_frame_image` 或 `last_frame_image`。
   - **编写视频提示词前先核对跨镜头状态**：实际查看上一个镜头的已生成视频或确认过的末帧，并对照本镜剧本、关键帧及镜头表；不要只看本镜静态关键帧。逐项判断角色的动作/移动方向、姿势、视线、手中道具与伤势，entity 的朝向、目标、肢体/攻击状态，以及场景中仍在进行的动作（如水柱、聚水、粒子、烟尘）、摄影机运动和由此产生的背景视差，哪些应延续、停止或在切镜后改变。**一并沿用前镜的环境状态**：剧本没有明确的时间、天气或环境光变化时，视频提示词须延续前镜的日夜、天空、主光方向、色温和整体曝光；除剧情明确发生的局部光效外，不要将整个场景重新解释为另一种环境。若剧情时间连续且上镜动作尚未结束，应把动作状态和运动感延续到本镜，并明确视频开始时的状态及整个镜头中的变化；例如人物仍在奔跑时，背景需随跟拍产生可见视差，仍在攻击的 entity 应保持攻击或按剧情进入下一动作，不能因参考关键帧背景静止就把环境写成静止。若是明确的时间/地点跳转或动作已完成，则按新状态起镜，不机械继承。只继承剧本与画面支持的内容，不补入画外或尚未发生的元素；连续性要求与关键帧构图冲突时，先判断是否需要修关键帧或镜头表，再写视频提示词。
   - 提示词内容按镜头形态选用 `prompts_structure/shot/minimax.md`（连续单镜）或 `prompts_structure/sequence/minimax.md`（含剪辑的序列）；不要在执行层重复模板里的台词、动作、负面约束等写法。Execution 在此阶段只负责绑定并核对参考素材、调用接口、监控任务、检查产物并记录状态。若只是希望模型从某个状态开始、朝某个状态结束，将对应图片作为普通参考图，并在提示词中写明“开场状态”与“目标结束状态”；这只提供视觉引导，不形成硬帧锁定。只有用户明确要求锁定首帧或首尾帧时，才改用对应帧字段；首尾帧锁定模式不与多参考图混用。应用接口限制见 `references/ai-image-video-generator.md`。
   - **Entity 参考图**：镜头涉及 entity 时，将该 entity 最完整、已确认的概念图直接作为 MiniMax 的设计参考，锁定身份、材质、结构和整体设计。再按具体镜头中 entity 实际出现的形态、尺度、构图位置和状态，生成一张镜头专用的单体参考图并一并提交；概念图负责“它是什么”，镜头专用图负责“它在本镜头里长什么样/处于什么状态”。在提示词中明确各图职责，镜头专用图需遵守关键帧的空间和构图。
   - **复杂特效单镜状态故事板**：当一个镜头内包含多阶段、仅靠文字难以说明的特效/形态变化（如粒子聚合、流体生物成形、实体转化为界面），为该镜头单独制作一张按顺序展示状态变化的故事板（约 3–5 格）；它只描述本镜特效过程，不替代覆盖多个镜头的场次故事板。简单、单一动作不需要另做。
   - **故事板统一使用纯黑白线稿**：所有单镜、多镜和特效状态故事板均按 storyboard 结构生成；每格保持 16:9，白底黑线，不用彩色、灰阶填充或写实成片画面。线稿只承担布局、动作/状态顺序和机位运动参考；清晰关键帧仍负责视频首帧与场景构图，高清概念图负责角色/entity 外观。避免视频模型把小格成片画面当作最终视觉外观照搬，或以低清格图替代高清外观来源。
   - 将特效状态故事板作为额外运动/阶段参考，与当前镜头关键帧、角色概念图、entity 概念图及镜头专用 entity 参考图一并绑定。提示词逐段写清“故事板第几格 → 视频多少秒 → entity 的可见状态与运动”，特别核对图中真实运动方向和先后顺序，不要用想当然的动作描述覆盖参考图。
   - **严格区分画面职责**：关键帧是视频第一帧以及整幅画面的构图、机位、场景、人物位置和空间关系的唯一权威；entity 概念图和镜头专用 entity 图限定 entity 的设计与本镜状态；过程图只限定该 entity/主体的特效变化流程、阶段顺序和运动方向。提示词要明确过程图只是局部特效动作参考，并要求该变化发生在关键帧对应的场景和位置中。过程图中的分格、编号、边框、背景和排版不属于视频画面，不能将其描述成镜头、分镜或视频构图，也不能让过程图取代关键帧。
   - **布局与设计分源**：故事板只传递布局、动作/状态顺序和机位变化；获批关键帧或场景概念图负责雕塑、建筑等固定造型，高清单体概念图负责人物/entity 外观。故事板不得重新设计已确认的场景物件；提交前逐格检查雕塑轮廓、池体等关键几何是否与获批来源一致。人物/entity 参考图可补充身份和设计，但不会提高视频本身的像素分辨率，也不保证细节逐项迁移；重要细节需在清晰首帧/画面参考中足够可见，并在提示词中按图分工。
   - 若特效的最终结果是屏幕、投影、符号或其他具有设计细节的画内图像，另行绑定清晰的最终图像参考；过程图负责变化顺序，entity 概念图负责设计权威，镜头专用图负责本镜头呈现状态，最终图负责完成态内容。
9. **回收与复盘**：全部镜头跑完后核对状态表，把新问题追加到 [references/lessons-learned.md](references/lessons-learned.md)。

各阶段的输入输出细节见 [references/pipeline.md](references/pipeline.md)。

## 状态跟踪

为每个镜头维护状态，任何时候都要能回答“哪一镜进行到哪一步”：

`pending → style_confirmed → anchors_ready → breakdown_confirmed → keyframe_ready → video_submitted → video_done`

异常态：`blocked(原因)`。任何镜头不得静默跳过——失败必须记录原因进入 blocked，本轮其余镜头跑完后统一回补。

## 执行纪律

- 单镜时长默认 ≤ 8 秒；超出时在拆镜阶段就拆成连续镜，并在 `continuity` 标注“尾帧续接”。
- 并发分开控制：本地提示词服务（如 11434）串行调用；渲染提交（ComfyUI / MiniMax）可适度并行。
- 自动提示词接口偶发超时时，允许绕过它手工组装视频提示词，但必须在状态记录里标注“手工提示词”。
- 开工前先确认渲染后端连通（如后端 status 里 `comfyui_connected=true`），不连通不批量提交。
- 已知坑先查 [references/lessons-learned.md](references/lessons-learned.md)，不要重复踩。
- 不把“已有单镜生成接口”误称为“已具备小说一键全自动生产”。若当前应用没有编排器，应明确执行到哪一个确认门，并逐镜记录或回填，而不是假定批处理、质检和重试已经发生。
- 当直接使用“场景锚图 + 人物锚图”生成关键帧后，仍出现机位、空间拓扑、姿态、身份或左右侧别错误时，不要无限强化一条提示词。若应用集成档案支持，改用其中的“三段式关键帧回退”。
